## 2. 关键设计决策

### 2.1 引导为什么做成「可重跑的四步向导」而不是一次性首启流程

低配 E-Ink 设备最常见的支持成本不是崩溃，而是**用户不知道该调什么**：性能档选错会卡、刷新模式选错会残影、按键没配就翻不了页。所以引导承担的是「把 EAL 的三个关键旋钮暴露一次」的职责，而不是播个欢迎页。

由此推出两条设计：

1. **每一步都是"改了立刻生效"**——性能档改完直接 `Eal.reload()`，刷新模式改完直接 `RefreshModeManager.apply()`。向导内部不缓存状态，避免"完成引导才生效"带来的二次困惑。
2. **允许从设置重跑**（`pref_rerun_onboarding`）。设备换手、换固件、用户想换性能档时不必清数据。用 `prefs.onboardingDone` 只控制**是否自动弹出**，不控制能否进入。

步骤机 `OnboardingStep` 是无 Android 依赖的纯枚举（`TIER / REFRESH / INPUT / IMPORT`），`next()/prev()/isFirst/isLast/humanIndex` 全在 JVM 上可测——向导最容易出的 bug 是首尾边界，这类 bug 不该靠手点去发现。

### 2.2 配置备份为什么用「类型化快照」而不是直接 dump SharedPreferences

最省事的做法是把 `SharedPreferences.getAll()` 直接序列化。这里没这么做，原因是三个具体的坑：

**坑一：会把 WebDAV 密码写进明文备份文件。**
`Snapshot` 是显式字段化的数据类，WebDAV 只带 `url / user / dir`，**密码字段根本不进快照**。恢复后密码保持原样，用户重填一次即可。这比"备份里带密码、再想办法加密"更安全，也更省事。

**坑二：Preferences 的类型会在往返中被抹平。**
`androidx.preference` 的 `EditTextPreference` 把整数存成 String，而代码里另一些项存的是 Int。`Snapshot` 用显式类型的字段（`Int` / `Float` / `Boolean` / `String`）承接，恢复时按字段类型写回，不依赖"存进去时是什么类型"。测试里专门钉了这条（`integer preferences survive the json round trip as integers`）。

**坑三：恢复应该是「替换」而不是「合并」。**
`allKeyMaps()` 拿到的键位映射表在恢复时是**整体替换**。如果做合并，用户的旧键位会和新键位混在一起，产生"一半按键是旧的"这种极难排查的状态。

另外 `parse()` 严格校验 `format == "readit-config"` 且 `version == 1`，不匹配直接拒绝——宁可报错让用户重导，也不要拿半懂的 JSON 去改用户的配置。

### 2.3 设备收集工具为什么复用 `DeviceProfileDb` 的序列化路径

`toProfileJson()` 不是手写 JSON 字符串，而是构造 `DeviceProfileDb` 对象后用 Gson 输出。这样做的直接收益是：**导出的设备档案与内置 `assets/device_profiles.json` 保证同构**，社区提交的档案可以原样合入资源文件，不需要人工转格式。

这里顺带修掉了一个**静默失败**的 bug：`DeviceProfile.inputKeys` 与 `DeviceProfile.fallbackRules` 原先没有 `@SerializedName`，而 JSON 里是 `input_keys` / `fallback_rules` 蛇形键。Gson 遇到对不上的键**不报错、只留空**——于是社区提交的键位表会被静默读成空表，表现为"某机型按键全不响应"，而日志里一个字都没有。已补 `@SerializedName`，并由 `DeviceReportTest` 反向钉住（导出的 JSON 必须含蛇形键，且能经 `DeviceProfileDb` 往返）。

### 2.4 按键探测为什么不猜未知 keycode

`KeyProbe` 只把**已知** keycode 映射为语义动作（`PAGE_UP` / `PAGE_DOWN` / `BACK` / `MENU`），未知 code 一律如实记录原始值、不做推断。

原因是这个工具的输出会变成别人的设备档案。一旦开始"猜"，一份错误的档案会污染整个设备数据库，而且错得很难发现——用户只会觉得"这机器适配得不好"。原始值比错误的语义值有用得多：社区拿到 `keyCode=131` 至少能去查，拿到被猜错的 `PAGE_DOWN` 就只能被误导。

探测期间 **不拦截 BACK**，保证用户随时能退出——工具不能变成困住用户的地方。

### 2.5 「0 崩溃」的延续：降级而不是抛异常

配置恢复与设备导出都走 SAF（`CreateDocument` / `OpenDocument`），失败路径全部落到 toast + 日志，不抛异常、不写坏数据。`ConfigBackup.restore()` 在写回任何一项之前先完成整个快照的解析与校验，**校验不过时一项都不写**，避免"写到一半失败"留下半套配置。

### 4.2 §3.4 体积红线治理（本轮重点）

**先出事**：P4 开发收尾时单包体积从 P3 的 18.72 MB 涨到 **21.13 MB**，同时突破了 §3.4 的 Universal 20MB 上限和「单 ABI 分包稳定低于 16MB」的分包目标，属于硬性违规。

把 APK 拆到 ZIP 条目级后，发现**两个叠加的根因**，且在文件体积里合计虚增了 8.25 MB：

| APK | 治理前 | 治理后 | 变化 |
|---|---|---|---|
| `app-arm64-v8a-debug.apk` | 21.131 MB | **12.881 MB** | −8.250 MB (−39.0%) |
| `app-armeabi-v7a-debug.apk` | 20.980 MB | **12.730 MB** | −8.250 MB (−39.3%) |

#### 根因一：AGP 增量打包留下的零字节空洞（4.302 MB）

治理前 arm64 包的实际账是：

```
文件体积        21.131 MB
├─ 各条目压缩后合计   16.719 MB   ← 真实内容
├─ 中央目录 + 尾部      0.110 MB
└─ 空洞（无主字节）     4.302 MB   ← 纯浪费
```

这些空洞夹在条目之间，**100% 是零字节**，最大的两处紧贴本会话新增的条目：

| 位置 | 大小 | 零字节占比 |
|---|---|---|
| `lib/arm64-v8a/libc++_shared.so` 之前 | 1.964 MB | 100% |
| `res/xml/network_security_config.xml` 之前 | 1.912 MB | 100% |
| `DebugProbesKt.bin` 之前 | 0.365 MB | 100% |
| `classes3.dex` 之前 | 0.027 MB | 100% |
| 其余 16 处（`res/layout/*` 等） | 合计 0.034 MB | ≈100% |

**`network_security_config.xml` 是 Phase 2 才新建的文件**——空洞正好长在新增条目之前，这是判断"空洞来自增量原地改写、而非内容本身变大"的决定性证据。`packageDebug` 复用上一版 APK 原位改写，条目被增删或移动后原位置未回收，就留下成片零字节。

**修复**：全量 clean 重建（删除 `app/build` 与 `build`）。重建后 `holes=0`，文件体积 12.881 MB 与内容 12.772 MB 对齐，差额只剩正常的打包开销（本地头 + 中央目录 + 4096 字节对齐尾）。

**结论**：这类空洞**不是内容问题，是构建卫生问题**。它不受代码影响、不会自己消失，只会随每次增量打包累积，因此已把「体检空洞」固化成工具（`tools/apk_size_check.py`），并写进 P4 的收尾流程。

#### 根因二：BouncyCastle 后量子密码查表资源（3.946 MB）

`com.tom-roush:pdfbox-android:2.0.27.0` 会传递引入 `bcprov-jdk15to18:1.72` / `bcpkix` / `bcutil`。jar 内的 Java 资源会被 AGP **原样打进 APK 根目录**，其中 5 个文件是 PQC 算法的常量查找表：

| 条目 | 压缩后 | 原始 |
|---|---|---|
| `org/bouncycastle/pqc/crypto/picnic/lowmc.properties` | 1.498 MB | 3.472 MB |
| `org/bouncycastle/pqc/crypto/sike/p751.properties` | 1.056 MB | 1.850 MB |
| `org/bouncycastle/pqc/crypto/sike/p610.properties` | 0.616 MB | 1.101 MB |
| `org/bouncycastle/pqc/crypto/sike/p503.properties` | 0.417 MB | 0.730 MB |
| `org/bouncycastle/pqc/crypto/sike/p434.properties` | 0.359 MB | 0.633 MB |
| **合计** | **3.946 MB** | **7.786 MB** |

本应用只通过 pdfbox 使用 BC 的**经典对称（AES/DES）与摘要（MD5/SHA）**实现来做 PDF 解密，PQC（Picnic / SIKE）代码路径永不进入，这 3.946 MB 是纯冗余。

**修复**（`app/build.gradle.kts`）：

```kotlin
packaging {
    resources {
        excludes += setOf(
            "/META-INF/AL2.0",
            "/META-INF/LGPL2.1",
            "/META-INF/DEPENDENCIES",
            "/META-INF/LICENSE*",
            "/org/bouncycastle/pqc/**",
            "org/bouncycastle/pqc/**"
        )
    }
}
```

#### ⚠️ 与 P3 文档结论的差异（重要）

P3 交付说明 §4 曾明确写下：「**排除 BouncyCastle —— 收益最大（3.96 MB），但不建议**：`PDDocument.load` 处理加密 PDF 时会引用 bc 类，排除后将抛 `NoClassDefFoundError`，直接违反 F08『0 崩溃』。」

**本次不是排除 BouncyCastle，与该结论不冲突。** 区别在于：

| | P3 中被否决的做法 | 本次实际做法 |
|---|---|---|
| BC 的类（dex 中） | 全部排除 | **完整保留** |
| BC 的 PQC 资源（APK 根目录） | 一并消失 | **仅排除这部分** |
| 加密 PDF 解密 | `NoClassDefFoundError` | **路径不变，正常工作** |
| 收益 | 3.96 MB | 3.946 MB（几乎等量） |

`packaging.resources.excludes` 只作用于**资源**，不影响 dex 中的类；而 `org.bouncycastle.pqc.**` 的**类**仍留在 dex 里（未开 R8），只是少了它们要读的 `.properties`。PQC 引擎类只会在被显式调用时加载资源，本应用不会走到那里。

**这一条也正是当初体积预算失准的原因**：§3.4 的预算表（App 6MB / epub.js 1MB / Pdfium 单 ABI 5MB / PdfBox 2.5MB / 其他 0.5MB ≈ 15MB）**根本没有把 BC 的传递依赖计入**，所以"稳低于 16MB"从一开始就站不住。补上 PQC 剔除后，实际结构与预算口径重新对齐。

#### 附带修复：PdfiumAndroid 的 JNI keep 规则

`proguard-rules.pro` 原先只 keep 了 `com.readit.**` 与 `com.tom_roush.pdfbox.**`，但 PdfiumAndroid 的渲染入口全是 JNI native 方法（`libjniPdfium.so` 按类名 + 方法签名反查）。一旦将来开启 R8，类名被改写会直接导致 `UnsatisfiedLinkError`、PDF 页白屏。已补：

```proguard
-keep class com.shockwave.pdfium.** { *; }
-dontwarn com.shockwave.pdfium.**
```

当前未开 R8（`isMinifyEnabled = false`），此规则是**为后续开启时预留的安全垫**，不影响本次产物。

## 6. 遗留与风险

1. **BC 的 PQC 类仍占 dex** —— 本次只剔除资源，`org.bouncycastle.pqc.**` 的类仍在 dex 中。若要进一步瘦身，需开启 R8 并保留 BC 的加密路径，属于独立动作，风险与收益需单独评估。当前余量充足，**不建议**现在动。
