## 3. 真机上发现并修复的缺陷

单元测试与 Robolectric 全部绿灯，但装到真机后**八种形态里有四种直接不可用**。逐条列清楚，因为这才是本轮交付的主体。

### 3.1 P0 · PDF 一打开就崩：`NoClassDefFoundError: android.support.v4.util.ArrayMap`

`com.shockwave.pdfium.PdfDocument` 的构造器里 `new` 了一个 `android.support.v4.util.ArrayMap`——即 **Pdfium 1.9.0 编译时依赖 support-v4，而不是 androidx**。项目此前在 `app/build.gradle.kts` 里留了一句"Pdfium 源码不使用 support-v4"的注释，判断是错的；依赖树全绿，是**运行时**才炸。

修复：

```kotlin
// gradle.properties
android.enableJetifier=true
```

```kotlin
// app/build.gradle.kts —— Jetifier 会把 PdfDocument 里的引用改写为 androidx.collection.ArrayMap，
// 显式声明保证它一定在运行时 classpath 上
implementation("androidx.collection:collection:1.1.0")
```

选 1.1.0 而不是 1.2.0，是因为本机 Gradle 缓存里只有 1.1.0；`ArrayMap` 的 API 面在这个版本已足够。

### 3.2 P0 · PDF 能打开但提取文本抛 `IOException: GlyphList .../glyphlist.txt not found`

真实异常是 `ExceptionInInitializerError: LegacyPDFStreamEngine.<clinit>`。因为 `GlyphList.load()` 在 `!isReady()` 时会回落到 `getResourceAsStream`（classpath）——JVM 测试里 classpath 上有 `glyphlist.txt`，所以**单测永远发现不了**；真机上该文件只存在于 AAR 的 `assets/`，必须显式把 `AssetManager` 绑给 PDFBox。

修复（`ReadItApp.onCreate()`）：

```kotlin
// PdfBox-Android 的 glyphlist/cmap/afm 是 AAR assets，任何 PDFBox API 之前必须先绑定 AssetManager
PDFBoxResourceLoader.init(this)
```

这一处同时让 JVM 测试与真机走了同一条资源路径，消掉了"测试能过、装机就挂"的缝。

### 3.3 P0 · EPUB 白屏：无渲染、无报错、logcat 里一个字都没有

`readit_epub/` 只带了 `epub.min.js` + `reader.html`，**漏了 JSZip**。epub.js 0.3.88 的 UMD 构建在脚本**执行那一刻**就把 `window.JSZip` 闭包捕获（`t.ePub = e(t.xmldom, t.JSZip)`），所以：

- 缺 JSZip → 书对象能建出来，`book.ready` 既不 resolve 也不 reject → **永久白屏**；
- 事后注入 JSZip 也无效（已经捕获过），必须**先**加载 JSZip；
- 随包的 `libs/jszip` 是 2.x，实例上没有 `loadAsync`，不能用。

修复：引入 JSZip v3.10.1（MIT/GPLv3），并在 `reader.html` 里固定加载顺序，注释写明"顺序不能改"。

同时补了一个之前完全缺失的东西：**`WebChromeClient.onConsoleMessage`**。在此之前 WebView 侧任何 JS 异常在 logcat 里都不可见，唯一现象就是白屏——这次是靠它才把问题定位下来的。

```kotlin
webChromeClient = object : WebChromeClient() {
    override fun onConsoleMessage(msg: ConsoleMessage): Boolean {
        // ERROR 走 e，其余走 w；返回 false 让 Chromium 也照常写一份
        ...
    }
}
```

### 3.4 P1 · 底部工具栏四个按钮**全部点不动**

这条最隐蔽：日志显示触摸事件被正常收到，但被错误消费了。

```
touch action=0 x=936 y=2223 mode=EPUB_FULL   ← 手指落在「设置」按钮上
touch up dx=0 dy=0 stage=(0,0,1080x2039)
handleAction=NEXT_PAGE                       ← 被当成"下一页"吃掉
```

`ReaderActivity.dispatchTouchEvent` 对**整个窗口**的点击都按 x 三分区映射并 `return true`，而底部的 目录/排版/刷新/设置 按钮 y 坐标在 stage 之外——于是它们永远收不到点击。「设置」按钮实测不跳转，直接印证。

修复：**只有"按下点落在 stage 之内"且"目录抽屉未打开"时才接管**，其余交还子 View。

```kotlin
downInStage = InputMapper.shouldHandleGesture(
    stageContainsTouch = stageRect.contains(ev.rawX.toInt(), ev.rawY.toInt()),
    drawerOpen = drawer.isDrawerOpen(GravityCompat.START)
)
```

两处细节值得留档：

1. 用 `rawX/rawY`（屏幕坐标）跟 `stage.getLocationOnScreen()` 比对，不用 `ev.x/y` 配 `stage.left/top`——后者混了"窗口坐标"和"父容器坐标"两套基准，正是这类 bug 的温床。
2. **抽屉必须排除**：抽屉是 `DrawerLayout` 的直接子节点，打开时**覆盖在 stage 之上**，如果只判矩形包含，抽屉里的 5 条 TOC 会一起点不动。

判定逻辑抽成了 `InputMapper.shouldHandleGesture()` 纯函数并补了用例，锁住这个回归点。

### 3.5 P1 · 页码先显示 `1 / 1`，翻页后才变对

`setDocument()` 发生在视图尚未测量时，`rebuild()` 提前返回；真正的分页是在 `onSizeChanged` 里算的，算完没有回调通知页码。另一个问题是 `totalPages()` 用的是"已算到哪算到哪"的 `starts.size`。

修复：`TxtPager.exactPageCount()`（带 `MAX_PAGE_GUARD` 上限，防脏文本死循环）+ `rebuild()` 末尾补 `notifyPageChanged()`。实测 TXT 首屏直接显示 `1 / 18`。

### 3.6 P2 · 加密 PDF 的提示文案是错的，而且一次弹两条

加密 PDF 在 Pdfium（渲染档）和 PdfBox（文本档）**都**读不了，于是通用降级链被完整走了一遍：

1. 先弹「PDF 渲染不可用，已切换为文本模式」——此时什么都还没切；
2. 文本提取也失败，再弹「该 PDF 没有可提取的文本层」，然后 `finish()` 回书架。

用户看到两条都不对的提示，且从头到尾不知道真实原因是"需要密码"。而 §9.3 第 5 行要求的是**"提示不支持，不崩溃"**。

修复：新增 `PdfOpenError.isEncrypted()`（在 cause 链上匹配 `password / decrypt / encrypted / encryption`，真机两侧文案分别是 `Cannot decrypt PDF, the password is incorrect` 与 `pdfium load failed: Password required or incorrect password.`）。命中加密就在扫描探测阶段**提前收口**，弹一个明确的对话框后停手，不再往注定失败的降级链里走。

关键回归点是：**不能误伤"可无密码读取的加密 PDF"**。`07_pdf_aes.pdf`（AES-128，空用户口令）本轮复测仍正常打开 20 页。

### 3.7 P2 · 启动图标在 MIUI 上是黑方块

只用一张 vector drawable 作 `android:icon`，API 26+ 的图标合成路径渲染成纯黑。改为 adaptive-icon（前景 vector + `@color/ic_launcher_background`）+ 5 档 mipmap PNG 兜底。

### 3.8 P3 · EPUB 渲染耗时埋点失真（会污染验收数字）

日志一度出现 `jsElapsed=34724ms`、`68798ms`、`72623ms` ——看着像 EPUB 渲染要一分钟。实际是 JS 侧算的是 `Date.now() - openStart`，而 `openStart` **只在首次 `open()` 时赋值**，之后每次重渲染都把"打开本书至今的总时长"当成单次渲染耗时上报。

修复：改成 `renderStart`，在 `open/display/displayCfi/next/prev` 每次导航前重置。修复后实测 `jsElapsed=150ms`。

顺带把 Kotlin 侧那句 `first chapter rendered in ...` 改对——它每次章节渲染都会打，原名会让人以为只有首章。

### 3.9 P1 · TXT 每页只排到实际容量的 1/5，屏幕下方大片空白

真机截图第一眼就看出来了：一页只显示 6~7 行，下面近 4/5 是空白，总页数 19 页。日志给出了线索：

```
TxtCanvasView rebuild: 1080x2039 charsPerLine=7 linesPerPage=29
```

1080px 宽、14sp 字号，**一行不可能只排 7 个汉字**。根因在标定算式：

```kotlin
val charW = paint.measureText(MEASURE_SAMPLE)   // MEASURE_SAMPLE = "汉字abc" —— 6 个字符的总宽度
charsPerLine = (maxWidth / charW).toInt()       // 却当成"单字宽度"去除
```

`measureText` 返回的是**整个样本串**的宽度，少除了一次样本字数，于是每行字数被低估约 6 倍。

后果不是崩溃，而是**版面缩水**：`charsPerLine × linesPerPage` 决定「本页取原文哪一段」，渲染层也只画这一段（`onDraw` 用 `paint.breakText` 真实换行，`y > bottomLimit` 就 `break`）。于是每页只取到 203 字（实际能排 ~660 字），剩下全是空白，**翻页次数凭空多 3~6 倍**——对电子墨水设备来说翻页正是最贵的操作。

修复：抽出 `TxtLayout.charsPerLine(maxWidthPx, sampleWidthPx, sampleCharCount)`，**显式除以样本字数**；样本也改成 10 个纯中文字（避免半角字符把基准拉窄）。`linesPerPage` 一并抽成 `TxtLayout.linesPerPage()`。

实测：`charsPerLine` 7 → **26**，总页数 19 → **5**，版面排满，且第 1 页末与第 2 页首**接续无跳字**。

**修的方向必须是「偏保守」**：标定值估小只会留白，估大则渲染层会把放不下的字**静默丢掉**（分页已经跳过它们了）。所以基准用最宽的全角字宽，宁可留一点白，不可丢字。

`TxtLayoutTest` 4 例钉住这个偏差，其中一例直接把「不除样本字数」的旧算法算一遍，断言两者差 5 倍以上。

## 4. 为什么这些缺陷单测抓不到

这不是"测试写少了"，是**两类环境差异**，值得写进后续回归清单：

| 缺陷 | JVM 测试为何通过 | 差异本质 |
|---|---|---|
| 3.1 Pdfium ArrayMap | 依赖树里没有 support-v4，Jetifier 关着也不报错 | 只在**运行时**解析类 |
| 3.2 GlyphList | Robolectric/classpath 上有 `glyphlist.txt` | **资源定位方式**不同（classpath vs AssetManager） |
| 3.3 EPUB 白屏 | 没有测 WebView 真实执行 | 需要**真实 Chromium** |
| 3.4 按钮点不动 | 没有 Activity 级触摸分发测试 | 需要**真实输入事件**与真实布局测量 |
| 3.9 每页只排 1/5 | `TxtPager` 本身是对的（用例都在它上面） | 错的是**喂给它的标定值**，标定发生在 `View.onSizeChanged` 里 |

结论：**"四种形态开机即挂"这类问题，必须靠真机冒烟兜住**，不能用单测绿灯替代。本轮把冒烟做成了可复跑脚本（§5.2），后续每次改动都能重跑。

补一条更普适的：**凡是"像素 → 容量"的换算，都值得抽成纯函数并单测**。3.9 这类偏差不会让任何测试变红，只会让用户体验静默缩水——它比崩溃更难被发现。

## 6. 仍未验证 / 未覆盖

按重要性排序，**不粉饰**：

1. **E-Ink 设备（KY-01L / 600×480 兜底线专项）——完全未取样。** 本轮全程在普通手机上跑。刷新模式（`RefreshModeManager`）在真机上走的是 `AUTO + onyx=false` 的通用分支，E-Ink 特有路径（残影、整屏刷新、局部刷新）一次都没验证过。
2. **双 SoC 性能基准——未取样。** 本轮设备 `EAL detect soc=A33_CLASS`（型号不在设备库，走了兜底档），只覆盖了**兜底档**这一种；文档里的低配/高配档位差异没有对照数据。
3. **§9.3 第 4 行（混合版 PDF）、第 6 行（损坏/超大扫描 PDF）——没有夹具，未覆盖。**
4. **PDF 密码输入 UI——未实现。** 规范只要求"提示不支持"，本轮按此实现；若后续要支持输入密码打开，需要新增对话框与重试链路。
5. **超大文档内存表现**（200MB+ 扫描 PDF）——未造夹具，1GB 设备上的 OOM 表现仍是纸面推论。
6. **夹具本身有缺陷**：`01_txt_chapters.txt` 把同一段正文**重复了 18 次**（每章 6 次 × 3 章），导致相邻页看起来一模一样，**没法只靠截图判断翻页是否真的生效**。本轮是靠页码计数器 + 第 1/2 页首尾接续来确认的。后续应把 TXT 夹具改成带行号/页标（像 PDF 夹具那样 `Page N line M`），让翻页可以肉眼验证。
7. **TXT 容量标定只覆盖了这一台设备的一种字号**（14sp / 1080×2039 可用区）。字号滑杆、边距滑杆、`600×800` 兜底分辨率下的标定值没有逐档验证；`linesPerPage` 的公式与 `onDraw` 的公式也**不是同一个表达式**（前者用 `bottom-top`，后者用 `descent-ascent`），当前偏保守所以安全，但属于需要收口的隐患。
